| ID | BAS-C10 |
| Experiment or failure mode | **Lost `ponderhit` after an instant opponent reply (1.10.1).** Two time forfeits by 1.10.0 in a Colosseum `120+1` 4T tournament with ponder on (Grand Blitz 4T, 2026-09-26): vs Rarog 2.4.0 in a tablebase-lost KBBP-vs-K ending, and vs Manta 1.2.0 holding mate in 3. In both the opponent replied in ~1 ms, so the GUI's `ponderhit` reached the UCI thread while the engine thread was still in `start_search`'s setup (Syzygy root probe/PV extension, hash resize), and `start_search` then reset `ponderhit_requested_` just before searching. The queued `PonderHit` copy sat behind the search on the same engine thread. A clocked ponder search therefore ran with no limit; one that reached its depth cap (depth 100 in the mate-in-3 game after ~2 s) waited in `wait_until_bestmove_allowed` for a ponderhit it had already discarded. |
| Disposition | **Fixed in 1.10.1; bench unchanged at 14,978,465.** Reproduced 5/5 on both incident positions and 4/4 in an ordinary middlegame with the 1.10.0 binary (Threads=4, `go ponder` then an immediate `ponderhit`), and 0/5 hangs after the fix. The flag is now owned by the UCI thread: set on `ponderhit`, reset on receipt of `go` in protocol order, never written by the engine thread (the queued `PonderHit` only clears `parameters_.ponder`). The same audit closed a sibling window for `stop`: the pre-search reset of a stale stop now re-checks the control epoch and restores a stop received during setup. Two engine-level tests (clocked ponder and depth-capped ponder, both with a pending hash resize to hold the setup window open) fail on the old source and pass on the new; a stale-ponderhit test and two protocol tests guard the new ownership rule. Not related to BAS-E57: its forfeits were ponder-off host stalls. Rarog 2.5.0-dev was confirmed by binary to share the lost-ponderhit defect and additionally to drop a `go ponder` stopped before it starts; reported to its own thread, not fixed here. |
| Conditional lesson / coverage | A control flag written by the input thread must not be reset by the worker thread that consumes it: the worker cannot know whether a set it overwrites is stale or merely early. Reset it where protocol order makes the answer certain -- on receipt of the command that begins its lifetime. A fast opponent reply is an ordinary game event, not an edge case, so every ponder-protocol test needs a zero-delay variant; the existing tests all waited 150 ms before `ponderhit` and could not see this. BAS-E57's zero-forfeit evidence was ponder-off and says nothing about ponder play. |
