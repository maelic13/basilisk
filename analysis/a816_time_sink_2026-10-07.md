# A.8.16 — The won-endgame time sink

- State / class: `READY_FOR_IMPLEMENTATION` for A.8.17; gate for A.8.18 below, `R2`
- Owner / date: agent, 2026-10-07
- Decision needed: none before implementation; A.8.18 is maintainer-run.

## Known evidence

**Evidence, the sink** (head `38fa890`, `build/release-pext`, no tables).
Position rec1, `7r/5R2/8/2k1PB2/8/4K3/8/8 w - - 0 86`, at
`wtime 60000 winc 600`:
- the move takes **32,313 ms** and plays `f7d7`;
- iterations 1–27 complete by 1,002 ms (depth 27: `cp 1014`, PV `f7d7`);
- depth 28 then fails high six times on the same move, at 3,076, 3,811,
  4,722, 6,521, 8,683 and 11,180 ms (+1185, +1279, +1420, +1631, +1947,
  +2421), each a full-depth re-search costing more than the one before;
- no iteration completes before the hard maximum, so the soft limit, which
  is checked only between iterations, never acts.

**Evidence, the limits are Stockfish's.** At game ply 170 the optimum is
4,701 ms and the maximum `min(0.8097 × 60,000 − 10, 6.873 × 4,701) = 32,310
ms`, exactly where the move ended. A maximum above half the clock is the
donor's formula working as written. Stockfish does not sink here because it
finishes iterations: it re-searches a fail-high shallower (`failedHighCnt`).
**The maximum is not the defect; the iteration is.** The maximum stays.

**Refused: the donor's mechanism.** BAS-D17 refuted the fail-high depth
reduction on Basilisk's WAC floor (137 → 119, under 130), with no retry
trigger. B.5's aspiration work owns any return to it.

## Hypotheses

- **H1 (leading):** the sink is an aspiration cascade on a move the search
  already prefers. Once the optimum has passed, a root fail-high on the
  previous iteration's best move proves only that the move is better than
  the window expected. Playing it at once spends what the cascade would
  waste, and changes no move.
- **H2:** the cascade is rare in real games, so the repair is clock hygiene
  with little Elo. The gate's job is then to show it costs nothing.

## Interactions

- **The end-of-iteration soft stop** (stability, score-drop, effort and
  instability scales) is untouched; the repair acts only inside the
  aspiration loop.
- **Pondering:** off, since the clock does not run until `ponderhit`.
- **Helpers:** only the main thread owns the clock; its return stops the
  pool, as today.
- **The pool merge:** unchanged; the main thread's result is the last
  completed iteration.
- **MultiPV:** line 1 runs the aspiration loop; the extra lines start only
  after it completes, so they are skipped when it stops.
- **A.8.8's bound lines:** a fail-high after 3 s prints its `lowerbound` line
  naming the same move, so the last line still describes `bestmove`.

## Implementation handoff (A.8.17, `I1`)

1. In `Searcher::search`'s aspiration loop, at a fail-high (`score >= asp_b`),
   after the bound line, end the search when all of these hold:
   - the main thread under time management (`soft_limit_ > 0`, not
     pondering, `thread_id_ == 0`);
   - depth > 1, and the fail-high move `pv_table_[0][0]` equals the last
     completed iteration's best move;
   - `elapsed_seconds() >= soft_limit_` (the optimum, unscaled).
   End it the way a stop does: the iteration is discarded, and the result
   stays the last completed iteration, whose move is the fail-high move.
2. Nothing else changes: no bench effect (bench has no clock), no MultiPV
   change, no helper change.
3. **Tests:**
   - an engine test: rec1 at `wtime 30000 winc 300` (optimum 2,286 ms,
     maximum 15,712 ms) answers `f7d7` in well under the maximum (under
     8 s). Before the repair it runs to the maximum. Skipped in
     unoptimised and sanitizer builds, which are too slow for the clock.
   - exact bench; release and sanitizer CTest;
   - `uci_probe.py clock` on rec1–rec3, KQvK and KRvK at `60000+600`,
     before and after.

## Prospective prediction (frozen before any gate game)

- rec1 at `60000+600`: about 4.7 s instead of 32.3 s, the same move.
- Other won endings (1.0–6.9 s today): unchanged or shorter.
- Strength at `3+0.03` on the standard book: **+1 Elo, 80% interval
  [−2, +4]**. The repair fires only in a cascade past the optimum, which is
  mostly a won position, and its saving goes to later moves.

## Falsifiers and stop conditions

- A different move played in any probe position: the condition is wrong.
- A time loss, or a gate interval below 0: return to research.

## Gate for A.8.18 (maintainer-run; registered before any game)

PLAN's text proposes `[0,3]` at `3+0.03` and a `10+0.1` direction check. The
evidence argues for less:
- The repair cannot change a move when it fires; it only saves clock.
- The saving is relative to the clock, so the time control does not change
  what it does.
- A `[0,3]` test of a +1 effect would most likely run to its cap.

So the gate is **the repair bracket `[−5, 5]` at `3+0.03`** on the standard
book (`sprt-repair.toml`), cap 4,000 pairs, zero time losses. The `10+0.1`
direction check is dropped, for the reasons above. Activation evidence is the
controlled clock probe in item 3, since the PGN does not record when the stop
fires.
